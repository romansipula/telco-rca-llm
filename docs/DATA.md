# Data: TelecomTS as used here

Source: [AliMaatouk/TelecomTS](https://huggingface.co/datasets/AliMaatouk/TelecomTS) (MIT), paper
arXiv:2510.06063, code github.com/Ali-maatouk/TelecomTS. Data is downloaded at run time by
`telco_rca.data.telecomts.TelecomTSAdapter`. Nothing from the dataset is committed here, apart from
derived predictions and metrics.

## What is used

* **Input:** only the anomalous windows, `anomalous/{jammer,synthetic/Zone_X}/<app>/processed/chunked.jsonl`,
  i.e. 1,235 windows of 128 steps × 100 ms (12.8 s) from 12 recordings. The anomaly is treated as
  already detected: the model gets the window plus the detector's anomalous interval
  (`anomalies.anomaly_duration`).
* **Labels:** `anomalies.type` (11 root causes), `anomalies.affected_kpis`, and
  `anomalies.troubleshooting_tickets` (parsed into Issue / Symptoms / Root Cause / Resolution).
* **Baseline for the evidence:**
  1. the window's own normal steps, when ≥16 of them lie outside the anomalous interval; otherwise
  2. the same recording's unflagged history before the window (≤5 min, ≥300 steps, read from
     `raw/metrics.csv`, causal). "Unflagged" means outside every labelled anomaly interval of that
     recording, i.e. what the upstream detector reported. No root-cause label is used; otherwise
  3. the normal recording of the same zone and application (`normal/stationary/Zone_X/no_congestion/<app>`).
     The jammer recordings mostly fall back to this source because they are jammed from start to end.
* **Not used as model input:**
  * `description`. The paper (App. F.1) says these were generated with GPT-o3 from structured
    summaries that included the anomaly symptoms taken from the tickets. That leaks the label.
  * `statistics`, and the `QnA` traces (see below).

## Provenance of the text fields (checked before use)

From the paper's main text (Sec. 3) and Appendices C, D and F.1, retrieved via a Kaggle kernel because
arxiv.org is blocked in this VM:

| field | generated by | used here? |
|---|---|---|
| troubleshooting tickets | **GPT-4.1** (OpenAI), from anomaly type + symptom template + times; human-in-the-loop review | yes: SFT targets for `resolution`, reference for metrics |
| network-level descriptions | **GPT-o3** (OpenAI), surface realisation of extracted features + ticket symptoms | no (label leakage) |
| reasoning traces (`QnA.*.reasoning`) | **Qwen3-32B**, via rejection sampling, conditioned on the ground-truth label | **no**: Qwen is a Chinese-origin model, so per the project rules training uses tickets only |

Quote (App. F.1): "These traces are synthesized using a large instruction-tuned language model
(Qwen3-32B) via rejection sampling over multiple candidate generations."

## Properties that shape the results

These figures come from `results/data_audit.json`, produced by `scripts/data_audit.py`.

* **The tickets are class templates.** Each of the 11 classes has exactly 1 distinct ticket and
  exactly 1 distinct `affected_kpis` list. So `affected_kpis` and `resolution` follow
  deterministically from the root cause. Once the class is right, a lookup reproduces them
  perfectly, and metrics on those fields mostly re-measure classification. Only the `explanation`
  can carry case-specific information. Our target explanation therefore combines the ticket's Issue
  and Root Cause sentences with one sentence built deterministically from this window's evidence
  (which affected KPIs actually deviate, in which direction and shape, and over which steps).
* **Windows overlap.** Inside a synthetic recording, consecutive windows start 3.2 s apart (stride 32
  of 128, i.e. 75% overlap). A window-level random split therefore puts near-copies of the same
  anomaly in train and test. TelecomTS' own `src/run.py` does exactly that
  (`dataset.train_test_split(test_size=0.2, seed=42)`). We do not use it as the main split, and we
  report it only to show the size of the leak.
* **Jamming is a recording-level label.** All 279 Jamming windows come from 3 separate jammer
  recordings that contain nothing else. Every Jamming window spans the whole window, so its own
  history is jammed as well. The Jamming class can therefore be recognised from recording-level
  background differences (e.g. RSRP level vs the zone's normal recording) instead of from the
  interference signature. Metrics are reported with and without Jamming. The paper's own RCA
  preprocessing (`preprocess(..., "root-cause analysis")`) drops Jamming as well, so the 10-class
  number is the one closer to Table 4.
* 593 of the 1,235 windows are anomalous over the whole window (no in-window baseline).

## Split

`configs/splits/telecomts_grouped_seed42.json` (generated by `telco-rca prepare --resplit`,
`telco_rca.data.split.grouped_stratified_split`): the group is the recording, so no recording
contributes to both sides. All 2^12 assignments of recordings to the test side are searched. The
chosen split is the one that keeps all 11 classes on both sides, comes closest to 25% test, and has
the smallest Jensen-Shannon divergence between the train and test class distributions (seed 42 for
tie-breaks). The official code repo does not define a group split (see above), so this one is used.

| split | recordings | windows |
|---|---|---|
| train | jammer/File, jammer/Twitch, synthetic A/File, A/Twitch, B/File, B/Twitch, C/File, C/Twitch, C/YouTube | 927 |
| test | jammer/YouTube, synthetic A/YouTube, B/YouTube | 308 |

Per-class counts are in `results/data_stats.json` and in the README.
The test side is the YouTube recordings of zones A and B plus the YouTube jammer recording. This
makes it a cross-recording (and partly cross-application) generalisation test.
